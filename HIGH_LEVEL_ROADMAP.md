# Android AI Camera — High-Level Roadmap

> Учебный pet-проект: нативное Android-приложение для локального обнаружения объектов камерой смартфона.
>
> **Цель обучения:** не просто собрать APK, а самостоятельно понимать, проектировать, реализовывать, тестировать и объяснять ключевые части системы.
>
> **Ориентир по функциональности:** [NAVAIv02](https://github.com/AshutoshRudraksh/NAVAIv02), но **не копируем Flutter/Dart-код**: создаём собственную реализацию на Kotlin.

## 1. Цель продукта и MVP

**MVP:** приложение открывает камеру, локально обнаруживает несколько объектов с помощью модели YOLO и рисует поверх предпросмотра рамки с классом и оценкой уверенности — без отправки кадров на сервер.

**Критерий успеха:** стабильно работает на реальном Android-телефоне, корректно переживает переключение приложения в фон и обратно, не блокирует UI во время inference; результаты можно объяснить по каждому этапу конвейера.

## 2. Технологический ориентир

| Область | Предпочтительный выбор | Зачем |
|---|---|---|
| Язык | Kotlin | Нативная Android-разработка |
| UI | Jetpack Compose + Material 3 | Декларативный интерфейс |
| IDE и сборка | Android Studio, Gradle/Kotlin DSL | Стандартный Android toolchain |
| Архитектура | UI → ViewModel → domain/data (по необходимости) | Разделение ответственности, UDF |
| Состояние и асинхронность | Coroutines + StateFlow | Реактивный UI и фоновые операции |
| Камера | CameraX (Preview + ImageAnalysis) | Получение кадров с управляемым жизненным циклом |
| Инференс | LiteRT / совместимый TensorFlow Lite runtime | Локальный запуск модели на устройстве |
| Модель | Компактная YOLO-модель в совместимом формате `.tflite` | Object detection; конкретную модель проверяем экспериментально |
| Тестирование | JUnit, Android instrumentation / Compose UI tests | Корректность математики, состояния и пользовательских сценариев |
| Профилирование | Android Studio Profiler, замеры latency/FPS | Проверяем реальную производительность |

> Версии SDK, Kotlin, AGP, Compose BOM, CameraX и LiteRT фиксируем **на старте проекта** по актуальной совместимости, а не прописываем сейчас наугад. Android-проект не обязан сразу содержать Room, Hilt, Retrofit и множество модулей.

## 3. Последовательность этапов

### Этап 0 — Подготовка окружения и фиксация решений

**Изучаем:** Android SDK, Gradle, устройство Android-проекта, запуск на реальном телефоне, Git.

**Делаем:** создаём отдельный репозиторий; запускаем пустое приложение на физическом телефоне через USB/ADB; фиксируем версии инструментария и короткие архитектурные решения (ADR).

**Definition of Done (DoD):** reproducible debug build; приложение стартует на телефоне; есть README с инструкцией по сборке; первый commit.

### Этап 1 — Kotlin для опытного Java-разработчика

**Изучаем:** nullable/non-nullable типы, data/sealed classes, extension functions, функции высшего порядка, коллекции, основы coroutines; сопоставляем с Java, но не проходим повторно азы ООП.

**Делаем:** небольшие самостоятельные упражнения и Kotlin-модели предметной области: `Detection`, `BoundingBox`, `CameraUiState`.

**DoD:** можешь объяснить ключевые различия с Java и самостоятельно написать простые типы и преобразования без шаблонов.

### Этап 2 — Jetpack Compose и управление состоянием

**Изучаем:** `@Composable`, `setContent`, recomposition, `remember`, state hoisting, однонаправленный поток данных (UDF), жизненный цикл Activity, `ViewModel`/`StateFlow`.

**Делаем:** экран приложения с mock-списком распознаваний, состояниями loading/error/ready и переключаемыми параметрами отображения — пока **без камеры**.

**DoD:** UI меняется от состояния без прямого управления View; экран переживает базовые изменения конфигурации без потери необходимого состояния; понимаешь причины рекомпозиции.

### Этап 3 — CameraX: превью и поток кадров

**Изучаем:** разрешение камеры, `Preview`, `ImageAnalysis`, `ImageProxy`, lifecycle binding, ориентация, backpressure, закрытие кадров.

**Делаем:** живое превью, простой frame analyzer (пока без ML), отображение разрешения и частоты анализируемых кадров.

**DoD:** камера открывается и освобождается корректно; переход в фон и обратно работает; UI остаётся отзывчивым; `ImageProxy` закрывается на всех путях обработки.

### Этап 4 — ML-фундамент на статическом изображении

**Изучаем:** классификация vs detection, обученная модель vs inference, тензор, shape, dtype, RGB/YUV, resize/letterbox, нормализация, выходы модели.

**Делаем:** отдельный пайплайн `Bitmap/image → preprocessing → LiteRT inference → raw output`; сначала на тестовом изображении, с замерами времени.

**DoD:** запуск модели на телефоне воспроизводим; формы входных и выходных тензоров проверены фактически; результат декодируется корректно для **выбранной** версии YOLO, а не по предположению.

### Этап 5 — Object Detection и геометрия

**Изучаем:** confidence score, bounding boxes, IoU, NMS (если требуется для конкретного экспорта), преобразование координат между моделью, кадром и Compose UI.

**Делаем:** детекции на фото и отображение рамок; модульные тесты для coordinate transforms, IoU/NMS и postprocessing; учитываем aspect ratio, cropping и поворот.

**DoD:** рамки совпадают с объектами на фото разных соотношений сторон; ошибки и пустые детекции обработаны; логика не зависит от UI-компонентов.

### Этап 6 — Real-time AI Camera (MVP)

**Изучаем:** producer–consumer pipeline, backpressure, обработка кадров вне main thread, отмена coroutines, потоки и race conditions, частота кадров vs задержка.

**Делаем:** `CameraX → preprocessing → YOLO → postprocessing → StateFlow → Compose overlay`; по необходимости пропускаем устаревшие кадры; не допускаем параллельных конфликтующих запусков модели.

**DoD:** стабильное real-time обнаружение нескольких объектов на физическом устройстве; отзывчивый интерфейс; контролируемая память; отсутствуют очевидные утечки камеры и интерпретатора; известны средняя задержка inference и частота обработки.

### Этап 7 — Качество, оптимизация и завершение

**Изучаем:** profiling, CPU/GPU/доступные delegates, влияние размера/квантизации модели, robustness, Android lifecycle, основы инструментального UI-тестирования.

**Делаем:** сравниваем хотя бы две конфигурации модели/выполнения, профилируем узкие места; добавляем обработку отказа в разрешении, логирование, README с архитектурной схемой и демонстрационными снимками/видео; оформляем release-ready debug/demo сборку.

**DoD:** задокументированы ограничения и результаты измерений **на конкретном телефоне**, основные сценарии протестированы, приложение можно собрать по README; выполнен личный архитектурный review.

## 4. Учебный процесс — договор с ментором

1. **Сначала гипотеза:** формулируешь, как должна работать новая часть и почему.
2. **Сначала твоя реализация:** пишешь код самостоятельно; наставник даёт подсказки и направляет, но не подменяет обучение генерацией проекта.
3. **Code review по смыслу:** обсуждаем не только синтаксис, но и lifetime, потоки, границы ответственности, ошибки, производительность.
4. **Retrieval practice:** перед новым этапом коротко воспроизводишь ключевые идеи предыдущих; раз в несколько занятий — задача без подсказок.
5. **Малые вертикальные срезы:** каждый этап заканчивается работающим результатом и коммитом/PR, а не только прочитанной теорией.
6. **Инженерный журнал:** в `docs/learning-log.md` кратко фиксируем «что понял / что было сложно / почему принято решение / что проверить потом».
7. **Без жёстких дат:** переход к следующему этапу зависит от DoD и понимания, а не календаря.

## 5. Управление объёмом

### В MVP входит

- Нативное приложение на Kotlin + Compose.
- Живое превью камеры.
- Локальное обнаружение объектов одной совместимой YOLO-моделью.
- Рамки, классы, confidence.
- Корректная обработка permission/lifecycle/errors.
- Минимальные тесты и замеры производительности.

### Не входит до завершения MVP

- Обучение собственной нейросети и сбор датасета.
- Облачные API/LLM и передача кадров в сеть.
- Голосовые команды, TTS, навигация для слабовидящих.
- Поддержка iOS, Flutter, собственный backend.
- Большая Clean Architecture с десятками модулей, Room/Retrofit/Hilt «на будущее».
- Требование 30/60 FPS без измерений и оценки железа.

### Возможные следующие итерации

Переключение YOLO-моделей; журнал обнаружений; голосовая озвучка; accessibility; измерение качества на собственном наборе изображений; обучение/дообучение модели; интеграция с NAS — только если появится настоящая задача.

## 6. Риски и как их проверить

| Риск | Стратегия |
|---|---|
| Модель `.tflite` не подходит выбранному runtime/операторам | Проверить загрузку, shape и один inference **до** интеграции с видео |
| Неверные рамки и повороты | Тесты координат, разные aspect ratio, визуальные проверки |
| Лаги и нагрев телефона | Фиксировать latency/FPS, ограничивать частоту inference, сравнивать lightweight модели |
| Утечки/краши при lifecycle | Проверки pause/resume, отказа в permission, повторного открытия камеры |
| Слишком много технологий сразу | Не добавлять зависимости и архитектурные слои без конкретного требования |
| Потеря контекста Kafka pet-проекта | Оставить периодические короткие сессии повторения и зафиксировать текущую точку проекта |

## 7. Связь с `order-processing-system`

Проект с Kafka **не закрываем**. Перед переключением сохраняем текущее состояние веток, нерешённые вопросы и следующий шаг в отдельной заметке. Пробный режим: основной фокус на Android, небольшие регулярные занятия для повторения Kafka и поддержания контекста. Соотношение времени гибкое; приоритет — законченные вертикальные этапы, а не две одновременно «вечные стройки».

## 8. Первый конкретный шаг

**Начинаем с Этапа 0:** проверяем установленные Java/JDK, Android SDK, ADB и Android Studio на Manjaro; создаём новый проект **Empty Activity (Jetpack Compose)** на Kotlin; подключаем телефон и добиваемся первого успешного запуска. Никакой YOLO и дополнительных библиотек, пока не будет работающей базовой сборки.

После этого делаем короткое знакомство с `MainActivity`, `setContent`, composable-функциями и первыми изменениями UI — всё руками.
